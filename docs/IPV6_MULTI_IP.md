## 1. 技术背景

- **opencode zen 支持 IPv6**：本工具默认规则让 `opencode.ai` 及子域名优先走 IPv6 通道。
- **国内运营商 IPv6 前缀**：移动/电信/联通的住宅宽带，光猫通常通过 DHCPv6-PD 直接拿到 **/60**（部分 /56）前缀，即 16（或 256）个 /64 子网。
- **基本结论**：在 IPv6 网络环境下，终端设备理论上拥有大量可用的公网地址资源，但操作系统默认仅使用其中首选的一个。

## 2. 核心认知

操作系统对出站连接的源地址选择（Linux/Windows 遵循 RFC 6724）是确定性的，存在固定的优先级策略（如同前缀优先、标签优先级、隐私地址偏好等）。即便网卡上配置了多个地址，不经干预的出站连接也只会固定使用系统选定的"首选"地址。

若希望在不同连接上呈现不同的源地址，需要在协议栈的特定环节引入干预机制。常见干预点包括但不限于：

- 网络地址转换（NAT）层面的源地址池
- 应用层通过 API 显式绑定源地址
- 基于策略路由的路径选择

## 3. 前提条件评估

在规划部署方案前，需先确认当前网络环境的 IPv6 前缀分配情况：

| 情况 | 说明 | 技术可行性 |
|---|---|---|
| `/60` 或 `/56`（PD 前缀委派） | 光猫拿到一个前缀，可划分多个 /64 子网 | 最具灵活性，可实现跨子网地址轮换 |
| 单个 `/64`（SLAAC） | 光猫仅分配一个子网 | 仅能在同一 /64 内变换主机位 |
| 无 IPv6 分配 | 光猫未启用 IPv6 或运营商未提供 | 需先完成 IPv6 基础配置 |

常见运营商 IPv6 前缀特征：电信 `240e:`、移动 `2409:`、联通 `2408:`，形态通常为 `240x:x:y::/60` 之类。

## 4. 方案 A（Linux 环境 · 本工具零改动）

**适用场景**：本工具运行于 Linux 系统，且该系统本身为网络出口设备（直接拨号或桥接模式），或使用者具备底层网关的管理权限。

**原理简述**：

在出口网卡上配置多个 /64 子网的 IPv6 地址（例如覆盖 /60 所包含的 16 个 /64），然后在网络层的出站地址转换（SNAT）环节，将新建连接的源地址映射至一个覆盖上述多个子网的地址区间。

每次新建连接时，内核会在该区间内选择当前未被占用的地址作为源地址。由于每条 SOCKS5 连接对应一条独立的 TCP 连接，因此不同请求将呈现不同的公网源地址，且本工具无需感知底层的地址分配逻辑。

**配置方向**（非具体命令）：

- 地址配置：需将所分配前缀下的多个 /64 子网各取一个地址添加至出口网卡
- 转换规则：需配置出站 NAT 规则，设定源地址转换范围覆盖前述所有子网

## 5. 方案 B（Windows 环境 · 需扩展本工具）

**适用场景**：本工具运行于 Windows 系统，或需要以更精细的方式控制每个连接的源地址选择。

**原理简述**：

将多个 /64 子网的 IPv6 地址添加至 Windows 网卡，然后在应用层（本工具的连接池模块）为每个新建连接调用绑定（bind）接口时，传入指定的源地址，实现轮换或随机选择。

**配置方向**（非具体命令）：

- 地址配置：需通过系统网络配置接口将多个 /64 子网的地址添加至目标网卡
- 代码扩展：本工具连接池已预留扩展点（`lib/pool/connection-pool.js` 的 `_connectOne` 方法），支持传入 `localAddress` 参数以实现源地址绑定

## 6. 技术观察

部分服务端可能基于客户端的 **/64 前缀段** 进行来源识别或流量调度。仅在同一个 /64 子网内变换主机位（`::1` ~ `::ffff`），对此类服务而言仍属于同一来源段。

若希望在连接间呈现不同的 /64 前缀段，则需要确保可用的地址池横跨多个独立的 /64 子网。前缀长度越大可用的独立子网越多（/60 含 16 个，/56 含 256 个），地址池的多样性相应提升。

## 7. 连通性验证

可通过标准 SOCKS5 客户端（如 `curl`）经本工具代理访问公网 IPv6 测试服务，以验证链路的 IPv6 连通性以及源地址配置是否按预期生效。

建议以多次独立请求的方式观察出口地址的变化情况。

## 8. 注意事项

- **仅在同一 /64 内变换主机位时**：虽可实现地址变化，但对按前缀段识别来源的服务效果有限；部分运营商对同 /64 内大量并发连接可能有流量控制策略。
- **IPv4 场景不适用**：单条 PPPoE 线路通常仅有一个公网 IPv4 地址，多 IPv4 出口需要多条物理链路或双拨，不属于本工具的解决范畴。
- **系统临时地址（RFC 8981 隐私扩展）**：操作系统自动生成的临时地址通常以小时为周期更换，而非按连接更换，与本工具的设计目标不同。
- **地址池位置**：地址池必须在实际公网出口设备上配置。若本工具运行于内网机器，而公网出口在上级路由器，则需在路由器层面实施相关策略。
- **防火墙策略**：添加的地址需确保未被出站防火墙规则拦截，建议在实施前了解当前防火墙的过滤策略。

## 9. 对本工具代码的影响

- 方案 A（Linux SNAT）：**零改动**，本工具无需修改任何代码。
- 方案 B（应用层绑定）：仅需在连接池模块增加"源地址池管理 + 轮换/随机选择逻辑"，DNS、协议解析、转发等模块均不受影响。
